# Execution

Execution executes prepared Code, Code recovery, service Agents and delegated Agent tasks. It validates original input/output Schemas and returns StepResult to Runtime. It never owns Run/Stage state, chooses routes, loads a project, or imports Runtime implementations.

`create-execution.ts` creates an independent executor. `execute-code.ts` validates Code outcomes; recovery validates `CodeRecovery` and calls only the declared `recover` entry. `execute-agent.ts` validates Agent output. `agent-tool.ts` parses Tool inputs/outputs once, binds a child Access lifetime and rejects unfinished capability uses before returning.

The shared declared-Tool boundary records `agent_tool_failed` for service and delegated execution, with the Tool name, sanitized error chain and `inputDigest`. The digest is SHA-256 of the original input's canonical JSON (object keys sorted in JavaScript string order); it can be compared with candidate references from retained State without recording arguments or error messages. It is diagnostic metadata, not a receipt or authorization. Non-JSON, accessor-bearing, cyclic, proxy and oversized inputs have no digest; collection never calls getters or `toJSON`. Existing failure and retry rules remain unchanged.

`model/` owns provider preparation, credentials, model transport, final-output handling, timing and framework adapters. Host selects the frozen execution policy and prepares resources. Provider streams must contain an explicit finish; truncation or cancellation cannot authorize an outcome or replay accepted Tools. Unknown transport/provider causes stay private while classified errors are projected externally.

Service Agents set Mastra's `modelSettings.maxRetries` to 3: up to four attempts for a request the SDK considers retryable, before a response stream opens. The SDK owns classification and backoff; no Agent, Tool or Run replay loop is added. Processor retries remain disabled. Timing logs record each attempt, retry start, stream opening, first adapter part and final attempt count. Recognized HTTP status and nested transport codes survive error projection; arbitrary provider messages remain private.

Tool input digests, connection subscriptions and raw-chunk diagnostics are collected only when debug logging is enabled. Provider completion checks remain active without logging. A Tool diagnostic write failure never replaces its original exception; execution owners retain responsibility for logger health checks.

Connection observation subscribes to Node/Undici diagnostics and socket lifecycle events without replacing fetch or changing socket, proxy or pool settings. Debug logs record request creation, sending headers/body, response headers/completion/error, and observable DNS/TCP/TLS phases with elapsed times. Request events are correlated by their request object; sending headers binds them to a connection ID and observed new/reused status. Pool connection and socket events use `association: initiating_context`, which does not prove that the triggering request used that connection. Missing phases can mean reuse, cached resolution, or an uninstrumented transport; `unobserved` is not evidence of no connection. No URLs, headers, addresses, request/response bodies or raw error messages are recorded. Subscribers are removed when observations end and cannot throw into the HTTP client.

The timing wrapper requests SDK raw chunks only to count OpenAI-compatible JSON chunks and classify their first choice's non-null `finish_reason` before mapping. It consumes those chunks locally; they never enter Agent processing or logs. `completion` records upstream markers, adapter finish parts, an allowlisted raw reason, and the mapping comparison. Unknown values are recorded only as `unrecognized`; no raw strings, text, Tool arguments, headers or credentials are retained. `unavailable` means no matching JSON chunks were observed, not proof that the provider omitted a marker. The SDK filters SSE `[DONE]` before exposing raw chunks, so these logs make no claim about that sentinel or raw HTTP framing. Missing and unknown reasons still fail under the existing completion rules.

These observations begin after SSE/JSON parsing. `missing` means no finish marker was observed in parsed first-choice JSON; an unterminated final SSE event can also produce that result. It does not prove the field was absent from network bytes. Local fixtures cover that boundary, valid finish reasons with and without `[DONE]`, and unknown reasons using the installed SDK. Historical `other` logs alone cannot distinguish these causes.

`delegated/` owns external Agent tasks, claims, serial Tool calls, assets and Tool/completion receipts. Runtime supplies a `CallScope`, a minimal wait handle and bound Access. Receipts cache the complete Tool operation, including ownership checks, final-submission decisions and cleanup. Concurrent and later retries receive the same final value or failure without replaying effects. Active receipts have a fixed capacity and no eviction. A closing Call retains its receipts for 30 minutes after all tracked activity settles. Successful completion is a submission receipt; callers query the Run separately.

`ServiceModelObserver` carries usage/budget observations, never business State or credentials. These metrics are optional and cannot determine capability authority or whether external work has settled. See [Kernel boundaries](../../README.md).
