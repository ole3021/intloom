# User knowledge

## K01 — Scope and baseline
This is a browser-only, single-user TodoMVC application managing one list. Only features introduced by the current or earlier Intent are active. Later intents introduce editing and bulk actions, then navigation and persistence; do not require future features early. There is no server, account, synchronization, remote database or deployment requirement. Title search, protection against deletion by submitting an empty edited title, and the later clearAll increment are not part of this baseline. Persist committed task data, but restoring and displaying tasks after a page refresh is not required. That does not authorize deleting previously saved data. This knowledge contains business facts and delegated decisions; summarize only the facts relevant to the actual question, and do not submit the whole knowledge as another intent.

## K02 — Identity, creation and list order
Each task has an independent identity, title and completed flag. Enter in the new-task field trims the title's leading and trailing whitespace, preserves internal spaces, appends one nonempty task as incomplete and clears the field. Empty or whitespace-only submissions do nothing; typing without Enter does not create a task. Equal titles are allowed and remain independent tasks. Preserve insertion order when editing, completing or filtering. On load, focus the new-task field. A genuinely empty full list hides the list body, toggle-all control and operation footer, while keeping the page title, new-task field and external help information. A filtered view with no matches still shows the footer when the full list is nonempty.

## K03 — Editing and deletion
Double-click any task title, including a completed one, to edit it in place with its current title and input focus. Hide that task's normal title, completion control and delete control during editing. Enter or blur commits the trimmed title and exits editing without changing identity, completion state or position. Enter followed by blur must not commit twice or accidentally delete the task. A committed empty or whitespace-only edited title deletes that task. Escape cancels editing and preserves the previous title, even if the draft was empty; a later blur must not save the cancelled draft. The hover-only delete control removes only its task, regardless of completion state. Titles are plain text: display and store characters such as <b>buy milk</b> literally rather than interpreting them as markup or executable content.

## K04 — Completion, counts and bulk operations
Individual completion changes immediately update the view without changing titles, identities, order or other tasks. Completed titles use a visible completion style. Toggle-all affects the entire list, including tasks hidden by the current filter. It is selected only when a nonempty list is entirely completed; reopening a task or adding an incomplete task deselects it. Clear completed appears whenever the full list has completed tasks and removes all of them, including hidden ones, while preserving incomplete tasks and their order. Hide it again when none remain. The remaining count always counts the full list's incomplete tasks, regardless of filter, with 0 items left, 1 item left and 2 items left wording and an emphasized number. A nonempty all-completed list still shows zero; an empty full list hides the operation footer. Every mutation updates counts, filter matches, bulk-control state and empty-list presentation consistently.

## K05 — Filters and address navigation
All shows every task, Active only incomplete tasks, and Completed only completed tasks. Filters are views of the same full list; they do not mutate it. Actions on a visible task affect that same task across views. An incomplete task added while viewing Completed joins the full list and count but remains hidden until an appropriate filter is selected. Use canonical hash routes #/, #/active and #/completed; no selected filter defaults to All. A consistent equivalent #!/ route form is also acceptable. Direct addresses, filter links and browser back/forward keep the selected control, address and visible list aligned. Navigation within the current page preserves tasks and relative order. Refresh must preserve the filter chosen by the address; restoring the old visible task list is outside this baseline. Address navigation depends on the filter semantics, so changes to either require checking their relationship.

## K06 — Persistence and refresh boundary
Use this browser's localStorage with a todos-[framework] key; the initial implementation is native ESM, so todos-vanilla is authorized. Implementations must not overwrite another implementation's storage key. After valid committed changes, automatically save the complete list's identities, trimmed titles, completion flags and insertion order. This includes tasks hidden by filtering and all deletion results; deleting the last task saves an empty list. Do not persist an unsubmitted new-task draft, a temporary edit draft, editing-session state or rejected empty input. Escape preserves the prior stored title. Starting or refreshing the page must not write an empty list over previously stored data. Restoration, merging or replacement of prior-session data and multi-tab coordination are not defined by this baseline; do not invent a confirmed policy if the workflow requires such a decision.

## K07 — Presentation and attribution
Use English controls and the visible title todos. The new-task placeholder is What needs to be done?. Use a light neutral background and a centered white single-column card, with a large thin muted-red heading, readable input and row text, fine row separators, modest shadow and a subtle stacked-paper effect. Narrow screens must fit without horizontal scrolling; long titles may wrap without covering controls. Completion controls are round, completed tasks have a green check and light-gray struck-through title, and the pale-red delete cross appears on row hover without shifting content. Editing replaces the title with an input having a clear border and focus state. In the compact footer, place the remaining count left, All/Active/Completed centrally and Clear completed right when applicable. Highlight the selected filter with a thin rounded muted-red border without jumping layout. Outside the card, always show Double-click to edit a todo, author/team attribution and a Part of TodoMVC link to https://todomvc.com/, including when the list is empty. IntLoom is an authorized author label; exact CSS dimensions may be chosen within this description.

## K08 — Workspace and engineering decisions
The starting workspace and formal Artifact/Record history come from a completed first Intent implementing task creation, individual completion and deletion. The current Intents extend that confirmed baseline with editing/bulk operations, then filters/persistence/presentation; preserve its existing files and earlier requirements. Keep index.html as the browser entry and source modules under src; separate state, view, navigation and persistence responsibilities as needed. Node.js 26.4.0+ and built-in Node libraries run development checks; business code runs in the browser and must not require Node APIs there. No framework, third-party business dependency, backend or bundler is needed. You may choose internal module names, stable task-ID generation and a local development serving command. Add focused Node tests for the modules you implement; the authorized host check may use node with args ["--test", "test/*.test.mjs"]. Existing workspace conventions and checks should remain usable. Browser UI automation, visual grading and comparison with historic output are outside the functional E2E pass criteria.
